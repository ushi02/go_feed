## 咕咕面板关闭时没有滑出动画（M5-3 界面，2026-11-01）
- **现象：** 打开咕咕时面板会从右边滑进来，关闭时却一下子就消失了。
- **原因：** 关闭时同时改了两个属性：`transform`（有过渡动画）和 `visibility: hidden`（没有过渡，立刻生效）。元素马上变得不可见，滑出去的动画虽然在播，但看不到。
- **解决：** 让 `visibility` 延迟到滑出结束后再变：`transition: transform 300ms ..., visibility 0s linear 300ms`；打开时把延迟设为 0，立刻可见。
- **验证：** 在浏览器里点关闭后 100ms 读 `getComputedStyle`：`visibility` 还是 `visible`，`transform` 正在往右移；400ms 后变成 `hidden`。
- **学到了：** `visibility` 也能参与过渡，但它是「一下子切换」的，要用延迟来控制切换的时间点。隐藏元素可以等动画播完以后再做。

## 用英文问咕咕，它还是用中文回答（M5-2 英文版，2026-11-01）
- **现象：** 提示词里加了「用户用什么语言说话，就用什么语言回答」。在一段原本是中文的对话里用英文提问，咕咕全部用中文回答。改了提示词以后，正文变成英文了，但推荐卡片上的理由还是中文。
- **原因：** 推测有两个（没法直接看到模型怎么想的）：一是对话历史全是中文，模型跟着上下文的语言走；二是卡片上的理由是 `propose_subscription` 工具的参数，这个参数的说明是中文写的，模型填参数时更多参照这份说明，而不是提示词里的规则。
- **解决：** 提示词改成「只看用户**最新一条消息**的语言，不管之前的对话用什么语言」，并点明工具的 reason 也要用这种语言；工具参数 reason 的说明里也加上「用和这次回答相同的语言写」。
- **验证：** 本地用真实的 DeepSeek 试：中文历史里用英文问，正文变成英文（理由仍是中文，所以才有第二处修改）；改完两处后在新对话里用英文问，正文和三张卡片的理由都是英文，并注明 Written in Chinese。模型的输出不是每次都一样，这只能说明「改完以后试了一次是对的」。
- **学到了：** 给模型的规则要写在它做决定的地方：回答的语言看提示词，工具参数看参数说明。规则写得模糊（「用户用什么语言」），模型会按自己的理解来，要写成可以照做的具体条件（「最新一条消息」）。

## 部署脚本没有 pipefail（M5-1 CD，2026-10-31）
- **现象：** 第一次自动部署成功后看日志，发现步骤的 shell 是 `/usr/bin/bash -e {0}`，没有 `-o pipefail`。
- **原因：** GitHub Actions 只有在步骤里明确写了 `shell: bash` 时，才会用 `bash -eo pipefail`；不写就只有 `-e`。没有 pipefail 时，`curl ... | jq ...` 这一行的成败只看最后的 jq，curl 失败了也不会停下来。我在本地模拟时手动加了 `-eo pipefail`，所以没测出来。
- **解决：** 部署步骤加上 `shell: bash`。顺便把 checkout、setup-go、setup-node 升级到 v7（旧版本用的 Node.js 20 已经停止维护），升级前逐个看了大版本的更新说明，确认对我们的用法没有影响。
- **验证：** push 以后 CI 的 `go`、`frontend` 通过；下一次部署的日志里，shell 那一行应该是 `bash --noprofile --norc -eo pipefail {0}`。
- **学到了：** 本地模拟要和真实环境的条件一致，连 shell 的启动参数也算。第一次在真实环境运行后，要回头看一遍日志，确认它跑的方式和自己以为的一样。

## deployhook 被打包进了 gin 和 gorm（M5-1 CD，2026-10-31）
- **现象：** 在服务器上编译 deployhook 时，下载列表里有 gin、gorm、quic-go、mongo-driver、protobuf。deployhook 只需要验证 JWT，用不到这些。编译出来的程序有 20MB。
- **原因：** 为了复用登录接口的限流代码，deployhook 导入了 `middleware` 包。这个包导入了 gin，还导入了 `account`，`account` 又导入了 gorm。Go 导入一个包时，会把它依赖的所有包一起编译进来。
- **解决：** 把限流的计数逻辑移到新的 `internal/ratelimit` 包，只用标准库。`middleware` 用它包一层 gin 中间件，deployhook 直接用它。限流逻辑还是同一份。
- **验证：** `go list -deps ./cmd/deployhook` 里第三方包只剩 go-oidc、go-jose、oauth2；程序从 20MB 变成 9.4MB；全部测试通过。
- **学到了：** 「复用代码」时要看看导入的包会连带进来什么。权限越大的程序，越要让它只包含必要的代码。可以用 `go list -deps` 检查一个程序实际依赖了哪些包。

## 自动部署用不了 AWS 的 OIDC，改成服务器自己验证（M5-1 CD，2026-10-31）
- **现象：** 按计划要在 IAM 里添加 GitHub 的 OIDC 身份提供商，但 IAM 左边菜单只有 Roles、Policies、IAM users、Root access management，没有 Identity providers。直接打开那个页面，提示 Feature unavailable，要先「Activate advanced features」。
- **原因：** 这个 AWS 账号是新版注册流程开的「项目」模式（用 Builder ID 登录）。查 AWS 文档：开启高级功能要先升级到 Paid plan，而且**不可逆**，开启后账号的花费上限会被永久取消。之前「不能切换区域」也是同一个原因。
- **解决：** 不开启高级功能。GitHub 的 OIDC 令牌是公开可验证的 JWT，所以改成服务器上的 deployhook 自己验证（`backend/internal/deployhook/`）。设计时又检查出两个问题并改掉了：原设计用 `git pull`，可能部署 CI 还没测完的新 commit，改成只部署令牌里的 commit；这样一来旧令牌可以被重放来回退版本，所以再加上「拒绝比当前版本旧的 commit」。
- **验证：** 本地测试覆盖伪造签名、`alg: none`、别的仓库/分支/事件/workflow、过期令牌、非法 sha、未测 commit、回退、限流，全部通过。改掉任意一项检查，对应的测试就会失败（试过「回退检查」和「分支检查」两项）。服务器上的实际部署等第 9 步做完后验证。
- **学到了：** 云服务的账号类型会限制能用的功能，选方案前要先确认功能在自己的账号里能不能用。另外，修一个漏洞可能带出新的漏洞（只部署指定 commit → 旧令牌可以回退），改完要重新检查一遍。

## SSH 卡住，被误判成「安全组记的是旧 IP」（部署第 4 步，2026-10-29～30）
- **现象：** 10-29 在本机执行 `ssh -i ~/.ssh/go-feed.pem ubuntu@13.236.88.164` 一直卡着，`ssh -v` 最后停在 `Connecting to ... port 22.`。10-30 Claude 从自己的沙箱测试：80/443 端口 0.2 秒左右被拒绝，22 端口 8 秒超时。于是判断「安全组只放行了你以前的 IP，后来 IP 变了」。
- **原因：** 诊断错了。打开安全组一看，SSH 规则里的 IP 就是当前的 `153.179.155.201`。沙箱连 `github.com:22` 也同样超时，说明是**沙箱自己不让连任何 22 端口**，和安全组无关。10-29 卡住的真正原因没能确定：规则没改过，第二天直接就能登录，所以很可能是当时本机网络或 VPN/代理的临时状态。
- **解决：** 什么都没改，10-30 从本机直接 SSH 登录成功。
- **验证：** 本机 SSH 成功，第 4 步（Docker、swap）和第 5 步（clone）都完成了。沙箱里对照测试 `github.com:22`，同样超时。
- **学到了：** 用一个本身就有限制的环境去测试，结果反映的可能是这个环境的问题，而不是服务器的问题。下结论前要先找一个**已知正常的对照组**（比如 `github.com:22`）测一下：对照组也失败，问题就出在测试环境。另外，「我推测是 X」和「我确认了是 X」要分开说，推测要写出来怎么去验证。

## 点「手动刷新」总是报错，自动轮询也从没启动过（M1 浏览器检查，2026-10-29）
- **现象：** 在浏览器里点订阅源旁边的 ↻，页面上出现红色报错 `Failed to execute 'json' on 'Response': Unexpected end of JSON input`。可服务器日志显示这次刷新成功了（202），Worker 也确实去抓了。
- **原因：** 刷新接口成功时返回 **202（已接受）**，没有响应内容。前端的 `request()` 只把 **204** 当成「没有内容」，碰到 202 仍然调用 `res.json()`，解析空字符串就抛出异常。异常让后面「记下这个源正在刷新」的代码没有执行，所以本来应该启动的自动轮询也没有启动。从 Codex 写的第一版起就是这样。
- **为什么之前没发现：** 后端的集成测试只检查了接口返回 202，这本身是对的；问题出在前端怎么处理这个响应，而前端没有测试。M1-4 的计划里写了「在浏览器中手动检查一遍」，一直没做，这次补做时才发现。
- **解决：** `request()` 不再按状态码判断，而是先读成文字，内容为空就不解析 JSON。以后哪个接口返回 202 或 204 都不会再出这个错。
- **验证：** 重新构建后在浏览器里点 ↻：不再报错，显示「已安排刷新」；页面自动拉了一次订阅列表，看到 Worker 已经抓完（数据库里 `last_fetched_at` 是几秒前），就停止了轮询。
- **学到了：** 「接口返回值正确」和「用户看到的结果正确」是两回事，中间还隔着前端。计划里写了「手动检查」的步骤就要真的去做，自动化测试覆盖不到的地方，正是手动检查要补上的。

## 错误信息里的 URL，让编造的链接「通过」了过滤（M3-3，2026-10-29）
- **现象：** 写 M3-3 时重读 M3-2 的代码发现：模型推荐一个不存在的博客，验证失败了，但回答里这个博客的链接没有被删掉。
- **原因：** 删链接的规则是「工具结果里出现过的 URL 才保留」。可验证失败时，错误信息也会作为工具结果交给模型，而真实的网络错误信息里通常带着 URL，例如 `Get "https://fake-blog.example/": no such host`。于是这个编造的 URL 被当成了「工具查出来的」。M3-2 的测试没发现，是因为测试里的假实现返回的错误是 `no such host`，恰好不带 URL。
- **解决：** 以 `error: ` 开头的工具结果（工具执行失败）不算可信来源。
- **验证：** 先把测试里的假实现改成和真实一样，在错误信息里带上 URL，测试失败，复现了问题；修改后通过。
- **学到了：** 测试用的假实现要尽量像真的。假实现「太干净」，测试就会漏掉真实环境里才有的情况。另外，「这个数据是从哪里来的、能不能信」要按来源区分：同样是工具结果，成功的数据可以信，失败的错误信息不行。

## MySQL 健康检查通过了，api 却连不上数据库（M4-1，2026-10-28）
- **现象：** 用空数据库第一次启动生产配置时，`docker compose up` 报 `container api is unhealthy` 后退出。api 日志里有好几行 `connect mysql: ... connection refused`，而 MySQL 的健康检查当时已经通过了。
- **原因：** MySQL 官方镜像第一次初始化时，会先启动一个**只监听 socket、不开 TCP 端口**的临时服务器，用来建库建用户，然后关掉它，再启动正式的服务器。健康检查用的是 `mysqladmin ping -h localhost`，`localhost` 会走 socket，所以连上临时服务器就判定「就绪」了。api 通过 TCP 连接 `mysql:3306`，这时正式服务器还没起来，于是被拒绝。只有第一次初始化才会出现，平时重启时数据目录已经存在，所以开发环境里一直没发现。
- **解决：** 健康检查改成 `-h 127.0.0.1`，强制走 TCP，临时服务器不开 TCP，就不会被误判为就绪。
- **验证：** `down -v` 删掉数据卷，从空库重新启动，api 一次成功，日志里没有 `connection refused`。
- **学到了：** 健康检查要检查「依赖方实际使用的那条路」，而不是「进程还活着」。另外同一次还发现：备份容器在 MySQL 就绪后马上跑了第一次备份，那时 api 还没建表，备份是空的。所以把它的依赖改成「等 api 健康」。说明启动顺序也是要验证的东西。
- **备注：** 开发用的 `docker-compose.yml` 也有同样的问题，2026-10-29 一起改了。验证时没有删开发库，而是另起一个临时 MySQL 容器，每 0.5 秒同时测两种 ping：socket ping 在第 4 秒就报就绪，但这时 TCP 查询失败；TCP ping 到第 7 秒才报就绪，这时查询成功。

## 我记得的 DeepSeek 模型名已经过时了（M3-1，2026-10-28）
- **现象：** 我原本打算用 `deepseek-chat` 这个模型名。写代码前先查了官方文档，发现现在的模型是 `deepseek-flash` 和 `deepseek-v4-pro`，而且「思考模式」默认是开着的。
- **原因：** 大模型 API 更新很快，模型名、默认参数都会变，记忆和旧教程里的写法不一定还能用。
- **解决：** 按文档写，默认用 `deepseek-flash`，并且做成可以用环境变量 `DEEPSEEK_MODEL` 更换，以后换模型不用改代码。思考模式显式关掉，不依赖默认值。
- **学到了：** 调用外部 API 之前先看当前的官方文档；容易变的东西做成配置，并且把依赖的默认值写明，而不是默默依赖它。

## 删掉的旧文章会「复活」，还会发给新订阅者（M2-5，2026-10-28）
- **现象：** 第一版清理直接删除了没人订阅的源里第 31 篇以后的旧文章（本地一次删了 20979 篇）。检查结果时我意识到一个问题，写测试复现：清理之后有人订阅这个源，拿到最新的 20 篇；再抓取一次，他的未读变成了 25 篇。
- **原因：** RSS 里通常列着最近几十到上百篇文章。数据库靠「这篇文章已经存在（`feed_id` + `guid_hash` 唯一）」来去重，整行删掉以后，下次抓取认不出它们，就当成新文章重新插入，再按「新文章」发给所有订阅者。
- **解决：** 不删行，只清空旧文章的正文（`content = NULL`）。量了一下，正文占了文章表约 87% 的空间（108.8 MB 对 15.8 MB），所以只清正文也能达到节省空间的目的；标题和摘要还在，旧文章仍然能被搜到（搜索结果本来就链接到原文）。
- **验证：** 复现测试先在旧实现上失败（20 → 25），改完后通过；在本地把清理过的 241 个源提前重新抓了一遍，旧版本删掉的 5009 篇被重新插入，新版本清理后只清了正文、行还在。
- **学到了：** 删除数据之前，先想清楚「还有谁依赖这些数据」。这里依赖它的是去重逻辑，它不是一个明显的「读取者」。另外，计划里的写法（「只保留最近 30 篇」）只是实现手段，真正的目标是节省空间，手段有问题时可以换。

## 故事：搜索为什么用 MySQL 自带的全文索引，而不是 Elasticsearch（M2-4，2026-10-28）

> 这一条写成可以直接在面试里讲的故事，大约两分钟。被问「做技术选型时怎么取舍」时用。

**背景。** 这个项目的核心卖点是「发现中文独立博客」：用户输入「分布式」「读书笔记」这样的关键词，从 1400 多个博客、约 4 万篇文章里找到相关的文章，顺手订阅写这篇文章的博客。

**难点：中文没有空格。** 英文按空格切词就能建索引，中文不行。「分布式系统」应该切成「分布式 / 系统」，要做到这一点需要中文分词词典。最直接的办法 `LIKE '%分布式%'` 不需要分词，但用不上索引，每次都要把 4 万篇文章从头到尾扫一遍，数据越多越慢。

**考虑过的方案：**
- **Elasticsearch + IK 中文分词**：业界最常用，功能最强（同义词、纠错、高亮、复杂排序）。但它跑在 JVM 上，官方建议至少几 GB 内存，而我的 VPS 只有 1～2 GB；还要额外解决「MySQL 里的数据怎么同步过去」的问题，多一个要运维、可能出故障的组件。
- **Meilisearch**：比 Elasticsearch 轻得多，单个程序就能跑，支持中文分词和拼写纠错。但同样要解决数据同步。
- **MySQL 8 自带的 FULLTEXT 索引 + ngram 分词器**：不需要词典，每相邻 2 个字切一刀（「分布式」→「分布」「布式」），搜索时检查这些片段是否连续出现。数据就在 MySQL 里，不用同步，事务里写进去的文章马上就能搜到。

**决定：先用 MySQL。** 理由有三个：一是规模，4 万篇文章对 MySQL 来说很小；二是资源，一台小 VPS 不应该为搜索单独付出几 GB 内存；三是一致性，同一个数据库里不存在「同步延迟」和「两边数据不一致」的问题。这个决定在 CLAUDE.md 里写成了约定：不引入 Redis、消息队列和 Elasticsearch。

**验证。** 先在临时库里用 SQL 试了 ngram 的行为（中文按短语匹配、多个词取交集、英文单词和单个字也能搜），再用真实数据搜了 11 个关键词，结果大多相关，每次查询都在 50ms 以内。另外专门写了测试，保证用户搜不到别人私人订阅的博客。

**诚实地说局限。** ngram 是「笨办法」，有代价：搜 `go` 也会命中 `google`；排序只看关键词出现的次数，所以摘要里写了 4 次「周末」的文章，会排在标题就叫「周末的 3 种过法」的文章前面；不支持同义词和拼写纠错。

**什么时候换。** 我给自己定了换方案的条件，而不是一开始就上最强的方案：
1. 先在 MySQL 里改进：给标题加权。
2. 如果文章多到 MySQL 的查询明显变慢，或者用户确实需要纠错、同义词，再换 Meilisearch（单台机器）或 OpenSearch（上云以后）。
3. chatbot 推荐需要「按意思找」（比如「适合新手的编程博客」），那是向量检索的场景，和关键词搜索是两回事，第一版不做。

**面试可能的追问：**
- 为什么不直接用 `LIKE`？→ 用不上索引，每次都要全表扫描，查询时间随数据量线性增长。
- ngram 的索引会不会很大？→ 会比原文大好几倍，所以只索引标题和 500 字以内的摘要，不索引正文。
- 换成 Elasticsearch 的话，数据怎么同步？→ 简单的做法是 Worker 入库后同时写一份；更可靠的做法是读 MySQL 的 binlog（比如用 Canal、Debezium），这正是我现在想避免的复杂度。

## 相关度公式对不上，第一个猜测是错的（M2-4，2026-10-28）
- **现象：** MySQL 文档说分数 = TF × IDF × IDF。用真实数据核对，TF 部分完全符合（出现 4 次和 3 次的分数比例正好是 4 : 3），但 IDF 照公式算是 4.51，实际是 4.31。
- **第一个猜测：** InnoDB 删除行时不会马上从全文索引里移除，所以「文章总数」里还算着删掉的行。于是重建了表（`ALTER TABLE entries ENGINE=InnoDB`）再算。
- **结果：** 重建后数值变成 4.07，离公式更远了，说明猜测是错的。InnoDB 用的文章总数是它内部维护的统计数。
- **为什么没继续查：** 同一次搜索里所有文章的 IDF 都一样，只影响分数的绝对值，不影响排序。花更多时间也不会改变任何设计。
- **学到了：** 有了猜测要马上验证，验证失败就承认；要判断弄清楚这件事值不值得，而不是一直挖下去。另外，在有 ngram 索引的表上 `ALTER TABLE ... ENGINE=InnoDB` 要重建整张表和索引，4 万行花了十几分钟，期间写入会被挡住，生产环境要避开。

## 全文搜索：命令行里中文全变成了 NULL 和 ???（M2-4，2026-10-28）
- **现象：** 用 `docker compose exec mysql mysql ...` 试 ngram 索引时，英文能搜到，中文全部返回 NULL；之前查摘要时中文也显示成 `???`。
- **原因：** 不是索引的问题，是 mysql 命令行客户端默认的连接字符集不是 utf8mb4，中文在发送过程中就已经变成乱码了。
- **解决：** 加上 `--default-character-set=utf8mb4`。程序本身的 DSN 里一直有 `charset=utf8mb4`，所以不受影响。
- **学到了：** 结果不对时，先确认输入是不是我以为的那样，再怀疑功能本身。

## 摘要里存的是原始 HTML，会污染搜索索引（M2-4，2026-10-28）
- **现象：** 随机看了几条 `entries.summary`，内容是 `<p>`、`&ldquo;`、`<a href=...>` 这样的原始 HTML。
- **原因：** 入库时直接把 feed 的 description 截取 4000 字存进去了，没有处理。
- **解决：** 新增 `fetcher.PlainText`：用 HTML 分词器只取文字，解码 `&ldquo;` 这类实体，丢掉 script 和 style，合并空白，截取前 500 字。没有 description 的 feed 改为从正文截取，这样也能被搜到。
- **遗留：** 已经入库的旧文章不会重新处理，摘要仍然是 HTML。中文搜索不受影响，但像 `div`、`href` 这样的词会搜到噪音。正式部署时数据库是空的，没有这个问题。
- **学到了：** 加新功能前，先看看要用的数据实际长什么样。

## 死掉的博客会被永远重试（M2-3，2026-10-28）
- **现象：** 第一次全量抓取，1426 个博客里有 517 个失败，大部分是博客已经不在了（404、返回的不是 feed）。
- **原因：** 退避最长 32 小时，之后就永远每 32 小时重试一次，代码里没有「放弃」这个状态。
- **解决：** 返回 410 Gone（HTTP 里「永久删除」的意思）立刻停止；其他失败要连续 10 次（约一周）才停止，因为 404 可能只是对方暂时出了问题。停止的状态记在新字段 `disabled_at`，**没有**直接改 `in_pool`，否则 Worker 重启重新导入博客池时会被改回来。用户手动刷新或新订阅时，会清掉这个标记再试一次。
- **为什么是 10 次而不是 Miniflux 的 3 次：** Miniflux 里每个源都有人订阅，停掉以后订阅者会自己点刷新。我们的博客池大多没人订阅，停掉以后没人会去恢复，误判的代价更高。
- **验证：** 4 个集成测试（410 立刻停止、第 10 次才停止而第 4 次不会、停止后不再被认领、刷新和订阅可以恢复），都先在旧代码上确认失败；外加一个 `isDead` 的表驱动单元测试。
- **学到了：** 重试逻辑要有终点。设计「放弃」的条件时，要考虑放弃以后谁来恢复。

## 故事：为什么抓 RSS 要用 goroutine（M2-2，2026-10-28）

> 这一条写成可以直接在面试里讲的故事，大约两分钟。

**背景。** 我的项目要给 1426 个中文独立博客定期抓 RSS。抓一个博客的时间，大部分花在**等对方网站回应**上：快的几十毫秒，慢的十几秒，最慢会等到 45 秒超时。我的程序在这段时间里什么都没做，只是在等。

**第一个想法：一个一个抓。** 实测平均每个源大约 1.8 秒，1452 次抓取一个接一个做，估计要 **40 多分钟**。而且只要有一个网站很慢，后面所有的源都得排队等它。

**第二个想法：一次全派出去。** Go 里开一个 goroutine 非常便宜，`go fetch(feed)` 一行就能让它在后台跑，那 1426 个源同时开 1426 个 goroutine 行不行？不行，原因有两个：
- 自己的机器扛不住：同时打开上千个网络连接，VPS 只有 1～2 GB 内存。
- 对别人不礼貌：一瞬间发出上千个请求，看起来像是在攻击；如果几个博客托管在同一个服务上，还可能被对方封掉 IP。

**最后的做法：固定 8 个工人 + 一条传送带。** 开 8 个 goroutine 当「工人」，它们之间用一个 **channel** 当「传送带」。另一个循环负责去数据库认领该抓的源，放上传送带；哪个工人空了，就拿下来去抓。传送带是**无缓冲**的：只有工人空着才放得上去，所以任何时候最多只有 8 个请求在跑，而且认领（占座）和真正开始抓几乎同时发生，不会出现占了座却在排队、租约白白过期的情况。

**结果。** 一轮 1452 次抓取用了 **5 分 25 秒**，比一个一个抓快了大约 8 倍。程序每轮结束时自动写一条日志，记录耗时和失败率。

**插曲：一跑真实数据就发现了 bug。** 第一轮的失败率是 39.7%。我按错误类型分组统计，发现除了「博客已经不在了」这种正常失败，还有三个是我自己的 bug（见下一条）。其中最严重的一个，会让程序每 2 分钟去骚扰同一个网站一次。**如果只在测试里跑几个假的 RSS 源，这些问题永远发现不了**，这是我这次最大的收获：功能做完以后，要用真实数据跑一遍，再按错误类型分组看结果。

**还要考虑：怎么停下来。** 部署新版本时，程序会收到停止信号，这时可能有 8 个抓取正在进行。我的处理是：停止认领新的源，取消正在进行的请求，把「占座」还回数据库，等 8 个工人都退出以后程序才结束。被打断的抓取**不算作这个源的失败**，否则每部署一次，就会有一批源被误判成失败，要等 1 小时以上才会再抓。这个行为有专门的测试，实测停止只用了 0.16 秒。

**面试可能的追问：**
- 为什么是 8 个？→ 这是一个保守的起点。瓶颈在对方网站，不在 CPU；以后可以根据日志里的耗时调整，或者做成配置。
- 怎么保证并发代码没有数据竞争？→ 用 `go test -race` 跑所有集成测试；多个工人同时累加的计数器用 `atomic.Int64`。
- 多台机器同时跑怎么办？→ 认领用的是 MySQL 的 `SELECT ... FOR UPDATE SKIP LOCKED` 加租约，多个 Worker 进程不会抢到同一个源。

## 全量抓取暴露的三个 bug（M2-2，2026-10-28）

### 1. 入库失败的源会每 2 分钟被重新抓一次
- **现象：** 一轮抓完以后，还有 36 个源一直处于「被占用」状态，而且同一批源被反复抓取。
- **原因：** 抓取前要先占座（租约，2 分钟有效）。原来的代码只在「HTTP 请求失败」时记录失败、设置退避；文章写进数据库失败时直接返回，既没还租约，也没记失败。2 分钟后租约过期，这个源又被认领，然后又失败……没有尽头。
- **解决：** 把「抓取」和「入库」合成一步，任何一步失败都走同一个退避逻辑（失败 1 次等 1 小时，之后每次翻倍，最多 32 小时）。唯一的例外是程序正在关闭，那时只还租约、不记失败。
- **验证：** 先写一个会让入库失败的测试，在旧代码上确认失败；修复后测试通过。再跑一轮真实抓取，没有源卡在占用状态。
- **学到了：** 一个操作有好几步时，要检查**每一步**失败后的状态是否正确，不能只处理最显眼的那一步。

### 2. 文章日期是「公元 1 年」，MySQL 存不进去
- **现象：** 67 次抓取报错 `Incorrect datetime value: '0000-00-00'`。
- **原因：** 有的 feed 里的日期解析出来是 Go 的零值时间（公元 1 年 1 月 1 日），而 MySQL 的 DATETIME 只支持 1000～9999 年。
- **解决：** 1970 年以前的日期一律当作「没有日期」，改用抓取时间排序。
- **验证：** 先写单元测试复现，修复后通过；第二轮真实抓取不再出现这个错误。
- **学到了：** 外部数据什么样的都有，进数据库之前要先检查范围。我自己写测试数据时也踩过同样的坑：忘了给 `next_fetch_at` 赋值，Go 的零值时间同样被 MySQL 拒绝了。

### 3. 博客池从 1426 行变成了 1577 行
- **现象：** Worker 每重启一次，博客池的行数就变多一些。
- **原因：** 有些博客的 RSS 地址会重定向到新地址，旧代码会把数据库里的 URL 改成新地址。Worker 重启后重新导入博客池，按原地址找不到这一行，就当成新博客又插入一行，同一个博客出现了两次。这段代码其实在 M1-3 的计划里就写了要删，当时漏掉了。
- **解决：** 源永远保留创建时的 URL，只有解析文章里的相对链接时，才用重定向后的地址。
- **验证：** 先写测试，用一个会 301 跳转的假服务器，在旧代码上确认失败；修复后通过。Worker 重启多次，行数不再增加。
- **学到了：** 「幂等」（重复执行结果不变）依赖于「用什么找到同一行」。如果别处的代码会悄悄修改这个查找依据，幂等就被破坏了。计划里列好的待办，做完一步要逐条核对。

## 博客池里有 143 个博客没有 RSS 地址（M2-1，2026-10-28）

- **原因：** 原始数据里有些博客只填了网站地址。

## 用 127.0.0.1 打开页面就登录不了（M1-5，2026-10-28）
- **现象：** 用 `localhost` 打开能登录，换成 `127.0.0.1` 就返回 403。
- **原因：** 防 CSRF 的 Origin 校验，是拿请求头里的 Origin 和配置里写死的 `http://localhost:15173` 逐字比较。换一个地址，哪怕指向同一台机器，也会被当成别的网站。
- **解决：** 前端改由 Go 直接提供，和 API 同源；校验改成比较 Origin 里的主机名和请求的 Host 头是否相同。不用配置，localhost、127.0.0.1 和正式域名都能用。
- **验证：** 表驱动单元测试覆盖 7 种情况，先在旧代码上确认失败；smoke 测试用 127.0.0.1 跑通了注册和登录。
- **顺带发现：** 将来放在 Caddy 后面时，Go 看到的客户端 IP 全都是 Caddy 的，所有用户会共用一个限流额度。所以加了 `TRUSTED_PROXIES`，只相信来自可信代理的 `X-Forwarded-For` 头。

## 「最新 20 篇」取的其实不是最新的（M1-3，2026-10-27）
- **现象：** 新订阅一个博客，得到的 20 篇未读不是发布时间最新的 20 篇。
- **原因：** 旧代码按数据库自增 id 取最大的 20 篇。id 只代表「入库的先后」，RSS 里文章的排列顺序不一定按时间，所以 id 的顺序不等于发布时间的顺序。
- **解决：** 改成写入扩散模型（`user_entries` 表），按发布时间 `sort_at` 取最新 20 篇。
- **验证：** 先写一个打乱发布顺序的测试，在旧代码上失败；修复后通过。
- **学到了：** 自增 id 只表示插入顺序，不能拿来当业务上的时间顺序。

## 订阅和第一次抓取同时发生，可能漏掉订阅者（M1-3，2026-10-27）
- **原因：** 订阅时要给用户补 20 篇文章，Worker 第一次抓完也要给所有订阅者补文章。两件事同时发生时，可能谁都以为对方会做，结果这个用户一篇都没拿到。
- **解决：** 两边都先 `SELECT ... FOR UPDATE` 锁住 feeds 表里的同一行，让它们排队执行。两边加锁的顺序一致，所以不会死锁。
- **学到了：** 两段代码会读写同一份数据时，先想清楚它们同时运行会怎样。

## 正文链接加了 `target="_blank"`，老文章却没变（M1-4，2026-10-27）
- **原因：** 正文是在**入库时**清理好再存的，新规则只对之后抓到的文章生效。
- **学到了：** 「存储时处理」读的时候快，代价是规则一改，已经存好的旧数据不会跟着变。

## Go 包之间循环引用（M1-1，2026-10-27）
- **现象：** 拆包时发现 `entry` 要引用 `subscription`，而 `subscription` 计算 baseline 时又用到了 `Entry` 类型，两个包会互相引用（Go 编译时会报 `import cycle not allowed`）。
- **解决：** 先画清楚依赖方向，再让 `subscription` 直接写表名 `Table("entries")`，不引用 `Entry` 类型，生成的 SQL 完全一样。各个 handler 都要用的小工具，放进一个不依赖任何业务包的 `httpx`。
- **学到了：** Go 不允许包之间循环引用，这会逼着你把依赖方向想清楚。

## SSRF 防护把测试用的假服务器也拦住了（M0，2026-10-27）
- **现象：** 集成测试要用 `httptest` 起一个假 RSS 服务器，但 fetcher 不允许访问它。
- **原因：** 为了防 SSRF，fetcher 不允许访问内网地址，而 httptest 服务器就在 127.0.0.1 上。
- **解决：** 把 IP 检查函数做成可以替换的变量，只在测试里换成放行本机的版本，生产代码的行为不变。
- **学到了：** 安全检查和可测试性会互相冲突，可以用「依赖注入」来解决，同时要保证生产环境的默认行为是安全的。
