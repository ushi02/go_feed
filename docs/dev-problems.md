# 开发问题记录

记录开发中真实遇到的问题。每条的格式是：**现象 → 原因 → 解决 → 怎么验证 → 学到了什么**。面试时被问「你遇到过什么困难」，从这里挑。

最新的写在最前面。

## 死掉的博客会被永远重试（M2-3，2026-10-28）
- **现象：** 第一次全量抓取，1426 个博客里有 517 个失败，大部分是博客已经不在了（404、返回的不是 feed）。
- **原因：** 退避最长 32 小时，之后就永远每 32 小时重试一次，代码里没有「放弃」这个状态。
- **解决：** 返回 410 Gone（HTTP 里「永久删除」的意思）立刻停止；其他失败要连续 10 次（约一周）才停止，因为 404 可能只是对方暂时出了问题。停止的状态记在新字段 `disabled_at`，**没有**直接改 `in_pool`，否则 Worker 重启重新导入博客池时会被改回来。用户手动刷新或新订阅时，会清掉这个标记再试一次。
- **为什么是 10 次而不是 Miniflux 的 3 次：** Miniflux 里每个源都有人订阅，停掉以后订阅者会自己点刷新。我们的博客池大多没人订阅，停掉以后没人会去恢复，误判的代价更高。
- **验证：** 4 个集成测试（410 立刻停止、第 10 次才停止而第 4 次不会、停止后不再被认领、刷新和订阅可以恢复），都先在旧代码上确认失败；外加一个 `isDead` 的表驱动单元测试。
- **学到了：** 重试逻辑要有终点。设计「放弃」的条件时，要考虑放弃以后谁来恢复。

## 故事：为什么抓 RSS 要用 goroutine（M2-2，2026-10-28）

> 这一条写成可以直接在面试里讲的故事，大约两分钟。

**背景。** 我的项目要给 1426 个中文独立博客定期抓 RSS。抓一个博客的时间，大部分花在**等对方网站回应**上：快的几十毫秒，慢的十几秒，最慢会等到 45 秒超时。我的程序在这段时间里什么都没做，只是在等。

**第一个想法：一个一个抓。** 实测平均每个源大约 1.8 秒，1452 次抓取一个接一个做，估计要 **40 多分钟**。而且只要有一个网站很慢，后面所有的源都得排队等它。

**第二个想法：一次全派出去。** Go 里开一个 goroutine 非常便宜，`go fetch(feed)` 一行就能让它在后台跑，那 1426 个源同时开 1426 个 goroutine 行不行？不行，原因有两个：
- 自己的机器扛不住：同时打开上千个网络连接，VPS 只有 1～2 GB 内存。
- 对别人不礼貌：一瞬间发出上千个请求，看起来像是在攻击；如果几个博客托管在同一个服务上，还可能被对方封掉 IP。

**最后的做法：固定 8 个工人 + 一条传送带。** 开 8 个 goroutine 当「工人」，它们之间用一个 **channel** 当「传送带」。另一个循环负责去数据库认领该抓的源，放上传送带；哪个工人空了，就拿下来去抓。传送带是**无缓冲**的：只有工人空着才放得上去，所以任何时候最多只有 8 个请求在跑，而且认领（占座）和真正开始抓几乎同时发生，不会出现占了座却在排队、租约白白过期的情况。

**结果。** 一轮 1452 次抓取用了 **5 分 25 秒**，比一个一个抓快了大约 8 倍。程序每轮结束时自动写一条日志，记录耗时和失败率。

**插曲：一跑真实数据就发现了 bug。** 第一轮的失败率是 39.7%。我按错误类型分组统计，发现除了「博客已经不在了」这种正常失败，还有三个是我自己的 bug（见下一条）。其中最严重的一个，会让程序每 2 分钟去骚扰同一个网站一次。**如果只在测试里跑几个假的 RSS 源，这些问题永远发现不了**，这是我这次最大的收获：功能做完以后，要用真实数据跑一遍，再按错误类型分组看结果。

**还要考虑：怎么停下来。** 部署新版本时，程序会收到停止信号，这时可能有 8 个抓取正在进行。我的处理是：停止认领新的源，取消正在进行的请求，把「占座」还回数据库，等 8 个工人都退出以后程序才结束。被打断的抓取**不算作这个源的失败**，否则每部署一次，就会有一批源被误判成失败，要等 1 小时以上才会再抓。这个行为有专门的测试，实测停止只用了 0.16 秒。

**面试可能的追问：**
- 为什么是 8 个？→ 这是一个保守的起点。瓶颈在对方网站，不在 CPU；以后可以根据日志里的耗时调整，或者做成配置。
- 怎么保证并发代码没有数据竞争？→ 用 `go test -race` 跑所有集成测试；多个工人同时累加的计数器用 `atomic.Int64`。
- 多台机器同时跑怎么办？→ 认领用的是 MySQL 的 `SELECT ... FOR UPDATE SKIP LOCKED` 加租约，多个 Worker 进程不会抢到同一个源。

## 全量抓取暴露的三个 bug（M2-2，2026-10-28）

### 1. 入库失败的源会每 2 分钟被重新抓一次
- **现象：** 一轮抓完以后，还有 36 个源一直处于「被占用」状态，而且同一批源被反复抓取。
- **原因：** 抓取前要先占座（租约，2 分钟有效）。原来的代码只在「HTTP 请求失败」时记录失败、设置退避；文章写进数据库失败时直接返回，既没还租约，也没记失败。2 分钟后租约过期，这个源又被认领，然后又失败……没有尽头。
- **解决：** 把「抓取」和「入库」合成一步，任何一步失败都走同一个退避逻辑（失败 1 次等 1 小时，之后每次翻倍，最多 32 小时）。唯一的例外是程序正在关闭，那时只还租约、不记失败。
- **验证：** 先写一个会让入库失败的测试，在旧代码上确认失败；修复后测试通过。再跑一轮真实抓取，没有源卡在占用状态。
- **学到了：** 一个操作有好几步时，要检查**每一步**失败后的状态是否正确，不能只处理最显眼的那一步。

### 2. 文章日期是「公元 1 年」，MySQL 存不进去
- **现象：** 67 次抓取报错 `Incorrect datetime value: '0000-00-00'`。
- **原因：** 有的 feed 里的日期解析出来是 Go 的零值时间（公元 1 年 1 月 1 日），而 MySQL 的 DATETIME 只支持 1000～9999 年。
- **解决：** 1970 年以前的日期一律当作「没有日期」，改用抓取时间排序。
- **验证：** 先写单元测试复现，修复后通过；第二轮真实抓取不再出现这个错误。
- **学到了：** 外部数据什么样的都有，进数据库之前要先检查范围。我自己写测试数据时也踩过同样的坑：忘了给 `next_fetch_at` 赋值，Go 的零值时间同样被 MySQL 拒绝了。

### 3. 博客池从 1426 行变成了 1577 行
- **现象：** Worker 每重启一次，博客池的行数就变多一些。
- **原因：** 有些博客的 RSS 地址会重定向到新地址，旧代码会把数据库里的 URL 改成新地址。Worker 重启后重新导入博客池，按原地址找不到这一行，就当成新博客又插入一行，同一个博客出现了两次。这段代码其实在 M1-3 的计划里就写了要删，当时漏掉了。
- **解决：** 源永远保留创建时的 URL，只有解析文章里的相对链接时，才用重定向后的地址。
- **验证：** 先写测试，用一个会 301 跳转的假服务器，在旧代码上确认失败；修复后通过。Worker 重启多次，行数不再增加。
- **学到了：** 「幂等」（重复执行结果不变）依赖于「用什么找到同一行」。如果别处的代码会悄悄修改这个查找依据，幂等就被破坏了。计划里列好的待办，做完一步要逐条核对。

## 博客池里有 143 个博客没有 RSS 地址（M2-1，2026-10-28）
- **现象：** 计划写的是导入约 1570 行，实际 CSV 里只有 1426 行有 RSS 地址。
- **原因：** 原始数据里有些博客只填了网站地址。
- **解决：** 只导入有 RSS 的行，跳过的行数写进日志。如果在导入时去这些网站自动查找 RSS，启动时就要访问上百个外部网站，又慢又不稳定，所以不做。
- **学到了：** 拿到外部数据，先统计一遍实际情况，再决定方案，不要只看计划里的估计。

## 用 127.0.0.1 打开页面就登录不了（M1-5，2026-10-28）
- **现象：** 用 `localhost` 打开能登录，换成 `127.0.0.1` 就返回 403。
- **原因：** 防 CSRF 的 Origin 校验，是拿请求头里的 Origin 和配置里写死的 `http://localhost:15173` 逐字比较。换一个地址，哪怕指向同一台机器，也会被当成别的网站。
- **解决：** 前端改由 Go 直接提供，和 API 同源；校验改成比较 Origin 里的主机名和请求的 Host 头是否相同。不用配置，localhost、127.0.0.1 和正式域名都能用。
- **验证：** 表驱动单元测试覆盖 7 种情况，先在旧代码上确认失败；smoke 测试用 127.0.0.1 跑通了注册和登录。
- **顺带发现：** 将来放在 Caddy 后面时，Go 看到的客户端 IP 全都是 Caddy 的，所有用户会共用一个限流额度。所以加了 `TRUSTED_PROXIES`，只相信来自可信代理的 `X-Forwarded-For` 头。

## 「最新 20 篇」取的其实不是最新的（M1-3，2026-10-27）
- **现象：** 新订阅一个博客，得到的 20 篇未读不是发布时间最新的 20 篇。
- **原因：** 旧代码按数据库自增 id 取最大的 20 篇。id 只代表「入库的先后」，RSS 里文章的排列顺序不一定按时间，所以 id 的顺序不等于发布时间的顺序。
- **解决：** 改成写入扩散模型（`user_entries` 表），按发布时间 `sort_at` 取最新 20 篇。
- **验证：** 先写一个打乱发布顺序的测试，在旧代码上失败；修复后通过。
- **学到了：** 自增 id 只表示插入顺序，不能拿来当业务上的时间顺序。

## 订阅和第一次抓取同时发生，可能漏掉订阅者（M1-3，2026-10-27）
- **原因：** 订阅时要给用户补 20 篇文章，Worker 第一次抓完也要给所有订阅者补文章。两件事同时发生时，可能谁都以为对方会做，结果这个用户一篇都没拿到。
- **解决：** 两边都先 `SELECT ... FOR UPDATE` 锁住 feeds 表里的同一行，让它们排队执行。两边加锁的顺序一致，所以不会死锁。
- **学到了：** 两段代码会读写同一份数据时，先想清楚它们同时运行会怎样。

## 正文链接加了 `target="_blank"`，老文章却没变（M1-4，2026-10-27）
- **原因：** 正文是在**入库时**清理好再存的，新规则只对之后抓到的文章生效。
- **学到了：** 「存储时处理」读的时候快，代价是规则一改，已经存好的旧数据不会跟着变。

## Go 包之间循环引用（M1-1，2026-10-27）
- **现象：** 拆包时发现 `entry` 要引用 `subscription`，而 `subscription` 计算 baseline 时又用到了 `Entry` 类型，两个包会互相引用（Go 编译时会报 `import cycle not allowed`）。
- **解决：** 先画清楚依赖方向，再让 `subscription` 直接写表名 `Table("entries")`，不引用 `Entry` 类型，生成的 SQL 完全一样。各个 handler 都要用的小工具，放进一个不依赖任何业务包的 `httpx`。
- **学到了：** Go 不允许包之间循环引用，这会逼着你把依赖方向想清楚。

## SSRF 防护把测试用的假服务器也拦住了（M0，2026-10-27）
- **现象：** 集成测试要用 `httptest` 起一个假 RSS 服务器，但 fetcher 不允许访问它。
- **原因：** 为了防 SSRF，fetcher 不允许访问内网地址，而 httptest 服务器就在 127.0.0.1 上。
- **解决：** 把 IP 检查函数做成可以替换的变量，只在测试里换成放行本机的版本，生产代码的行为不变。
- **学到了：** 安全检查和可测试性会互相冲突，可以用「依赖注入」来解决，同时要保证生产环境的默认行为是安全的。
