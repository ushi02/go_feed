04每个业务模块里的四个文件

照着 feedsystem_video_go 的结构来。以 entry/（文章）为例：

文件餐厅角色做什么
entity.go菜品的定义「一篇文章」有哪些字段：标题、链接、正文……
handler.go服务员接收 HTTP 请求，检查参数，调用 service，把结果返回给页面
service.go厨师业务规则，比如「只能修改自己订阅里的文章」
repo.go仓库管理员唯一直接和 MySQL 打交道的地方，负责执行 SQL
分层的好处：每个文件只管一件事。改数据库查询不会影响接口，改接口格式也不会影响业务规则；测试时也可以单独测某一层。

05数据存在哪里

全部都在 MySQL 里，主要有这些表：

表存什么举例
users账号你的用户名、加密后的密码
sessions登录状态「这个浏览器已经登录为 ushi」

06一次点击的旅程：点开一篇文章

  1. 你在页面上点了一篇文章。前端发出请求：PATCH /api/entries/416/state {"read": true}
  2. 请求先经过 middleware/：检查 Cookie，确认你已经登录，是 ushi。
  3. 路由表 http/router.go 把这个请求交给 entry/handler.go。
  4. handler 调用 entry/service.go，确认这篇文章确实在你的订阅里。
  5. service 调用 entry/repo.go，执行 SQL：UPDATE user_entries SET read=1 WHERE user_id=… AND entry_id=416
  6. 处理成功后，页面把这篇文章变成灰色，侧栏的未读数减 1。

这篇文章之所以会出现在数据库里，是因为之前 Worker（cmd/worker → worker/ → fetcher/）抓到了 RSS，把它存进 entries，同时给每个订阅者在 user_entries 里插了一行「未读」。这就是写入扩散（fan-out on write）。

07Session 和 JWT 是一个东西吗？

不是，但它们解决的是同一个问题：HTTP 本身不记得你是谁，每个请求都是独立的。登录之后，服务器得有办法在后续请求里认出「这是 ushi」。两者是两种不同的做法：

Session 本项目在用

像寄存处的号码牌：

  • 登录时，服务器生成一串随机号码，在 sessions 表里记下「号码 → ushi」
  • 号码交给浏览器，存在 Cookie 里
  • 之后每次请求，服务器拿号码去查表，就知道你是谁
  • 退出登录时删掉这一行，号码立即作废

JWT video 项目在用

像盖了公章的通行证：

  • 登录时，服务器把「user_id=ushi，有效期到某时」写在凭证上，再用密钥签名
  • 服务器不存储它，只验证签名是否真实
  • 优点：不用查数据库，适合多个服务共同验证
  • 缺点：在过期之前很难提前作废，所以通常要搭配短有效期加 Refresh Token
容易混淆的一点：Cookie 只是「把凭证放在哪里」的问题，和「用 Session 还是 JWT」无关。JWT 也可以放在 Cookie 里。本项目只给浏览器用，退出后要能立刻失效，所以用 Session + HttpOnly Cookie。面试里可以讲这个取舍。

08硬盘在哪里？

硬盘的英文是 disk（完整说法是 hard disk drive，简称 HDD）。现在的电脑和服务器大多用 SSD（Solid State Drive，固态硬盘）。日常交流中，「存储」一般说 storage。

场景数据实际在哪里
本地开发（Mac）Mac 里的 SSD。Mac 上的 Docker 其实运行在一个小型 Linux 虚拟机里，MySQL 的数据存在 Docker 的数据卷（volume）中。这个数据卷位于虚拟机的磁盘文件里，就在你的 Mac 上。删掉容器不会丢数据，但执行 docker compose down -v 会连数据卷一起删掉。
部署到 VPS云服务商机房里的物理硬盘。分给你的是一块虚拟磁盘（block storage），一般有 25GB 以上。服务器关机后数据还在，但删除服务器时，数据会一起消失，所以需要备份。
内存（memory / RAM）和硬盘是两回事：内存速度快，但断电就清空，用来放「正在用的东西」；硬盘速度慢一些，但能长期保存。MySQL 会把常用的数据从硬盘缓存到内存里，以加快读取。

09存储模型：三张核心表

核心思想：一个博客只存一份，一篇文章只存一份，每个人的阅读状态单独存。 博客池里的博客和你订阅的博客放在同一张表里，用标记区分。

feeds（博客源）
 id | url                          | in_pool | 订阅人数 | 下次抓取时间
 12 | feeds.feedburner.com/ruanyifeng | true    | 1      | 6 小时后   ← 有人订阅：6 小时抓一次
 88 | example-blog.com/feed        | true    | 0      | 明天      ← 只在博客池里：每天抓一次

entries（文章，所有人共享）
 id  | feed_id | title             | content（完整正文） | search_text（标题+摘要）
 416 | 12      | 科技爱好者周刊 416 | <p>……</p>        | 科技爱好者周刊 416 本周……

user_entries（个人状态，只有订阅者才有）
 user_id | entry_id | read_at          | starred_at
 ushi    | 416      | 2026-10-27 09:00 | NULL
 xiaoming| 416      | NULL             | NULL        ← 小明还没读

各种操作发生时，三张表的变化

发生了什么表的变化
导入中文独立博客列表feeds 增加约 1570 行，in_pool=true
Worker 抓到新文章entries 增加一行；如果有订阅者，就给每个订阅者在 user_entries 插入一行未读（写入扩散）
你订阅一个博客subscriptions 增加一行；按发布时间取最近 20 篇，在 user_entries 里插入未读记录
你读了一篇文章把你那一行的 read_at 设为当前时间，别人的不受影响
全部标为已读UPDATE user_entries SET read_at=NOW() WHERE user_id=你 AND read_at IS NULL
侧栏未读数SELECT feed_id, COUNT(*) … WHERE user_id=你 AND read_at IS NULL GROUP BY feed_id
取消订阅删除这条订阅，以及你在这个博客下的 user_entries（收藏的保留）。博客和文章本身不删，别人可能还在订阅，它也可能还在博客池里
搜索某个话题只在 search_text 上走全文索引，不扫描完整正文，所以索引小、速度快
定期清理没有订阅者的博客，每个只保留最近 30 篇；被人收藏的文章永远不删
为什么要「统一存储」？一篇文章不会因为「在博客池里」还是「有人订阅」而变成不同的东西，分开存反而会出现两份数据、两套逻辑。统一之后，有没有订阅者只影响两件事：抓取频率，以及有没有 user_entries。

几个新名词

名词大白话
反向代理（reverse proxy）站在最前面的门卫，替后面的程序接收所有请求，再转交进去。Caddy 和 Nginx 都是反向代理
HTTPS 证书证明「这个网站确实是你的域名」，并且对传输内容加密。没有证书时，浏览器会显示「不安全」
端口（port）一台服务器上的「门牌号」。80 是 HTTP，443 是 HTTPS，3306 是 MySQL。对外开放的门越少越安全
.env 文件存放密码和密钥的文件，程序启动时读取。不放进代码仓库，防止泄露
mysqldumpMySQL 自带的工具，把整个数据库导出成一个 SQL 文件，可以用来恢复数据

11测试安全网（M0）

重构之前先写测试，好比搬家前先给每样东西拍照。搬完以后对照照片，就知道有没有东西摔坏或丢了。

测试测什么依赖
集成测试 backend/internal/http/integration_test.go走一遍完整流程：注册 → 订阅 → Worker 抓取 → 列出未读 → 标为已读。只通过 HTTP 接口操作，不调用内部函数真实的 MySQL（testcontainers 临时启动一个 Docker 容器）和假 RSS 服务器（httptest）
单元测试 backend/internal/fetcher/fetch_test.goCanonical（URL 规范化）、allowedIP（哪些 IP 禁止访问），以及抓取时的 304、2 MiB 大小上限、重定向到内网地址不需要数据库，不到 1 秒就能跑完

为什么集成测试只通过 HTTP 接口操作？

M1 会把 internal/reader/ 拆成好几个包，内部函数的名字和位置都会变。如果测试直接调用内部函数，重构时测试也得跟着改，就起不到安全网的作用了。HTTP 接口在重构前后保持不变，所以测试基本不用改。

为什么要让 IP 检查「可注入」？

SSRF 防护会拒绝访问 127.0.0.1，而 httptest 服务器恰好运行在本机，测试会被自己的防护挡住。所以把检查函数做成了一个变量 fetcher.IPAllowed，测试时替换成「放行本机」的版本，测完再换回原来的函数。生产代码的行为完全不变。

检验测试是否有效的方法：故意把代码改坏，看测试会不会失败。这次把「标为已读」改成什么都不做，集成测试马上报错 unread entries after mark-read = 3, want 0。这种做法叫 mutation testing（变异测试）。
go test -short ./... 会跳过集成测试，没有 Docker 时可以这样跑；CI（.github/workflows/ci.yml）每次 push 都会完整执行 go vet 和 go test -race。
