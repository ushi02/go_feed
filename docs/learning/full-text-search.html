全文搜索：从输入关键词到看到结果

在侧栏输入「分布式」，不到 50 毫秒就从约 4 万篇文章里找出相关的 30 篇。这一页解释它是怎么做到的、为什么这样选，以及还有哪些更好的方案。

倒排索引中文怎么切词索引建在哪 一次搜索的流程用户输入怎么处理相关度怎么算 局限其他搜索方案面试怎么讲
对应 M2 第 4 步（2026-10-28）。代码在 backend/internal/search/，数据库迁移在 00004_entry_search.sql。

01核心概念：倒排索引

想象一本书最后的索引页：想找「分布式」在哪儿讲过，不用从头翻到尾，查索引页就知道在第 12 页和第 87 页。

数据库的全文索引就是这样一张索引页，只不过「页码」换成了文章 id：

普通的存法：文章 → 内容

  • 文章 1：「用 Go 写分布式系统」
  • 文章 3：「系统设计入门」
  • 文章 7：「分布式锁的坑」

倒排索引：词 → 哪些文章

  • 分布 → 1、7
  • 布式 → 1、7
  • 系统 → 1、3

方向和普通的存法正好相反，所以叫倒排。搜索时直接查这张表，不用逐篇去读。

对比 WHERE title LIKE '%分布式%'：它用不上索引，每次都要把 4 万篇文章全部读一遍（全表扫描），数据越多越慢。倒排索引的查询时间基本只和「命中了多少篇」有关。

02难点：中文没有空格，怎么切词

英文天然用空格分隔：Learning Golang channels 切成 3 个词就行。中文的「分布式系统」应该切成「分布式 / 系统」，要切准，需要一本中文分词词典。

MySQL 的 ngram 分词器用了一个笨但有效的办法：不管意思，每相邻 2 个字切一刀（2 这个长度由 ngram_token_size 决定，默认就是 2）。

分布式系统原文
↓每相邻 2 个字切一刀
分布
布式
式系没有意思，也照存
系统

搜索时用同样的方法切：搜「分布式」就变成「分布」「布式」，然后检查文章里是不是按顺序连续出现了这两个片段。连续出现才算命中，所以搜「布系」不会误中「分布式系统」。

实测过的行为

搜索能不能搜到原因
分布式能「分布」「布式」连续出现
布系不会误中「分布式系统」里没有连续的「布系」
golang、rust能英文同样按 2 个字母切片
山（单个字）能比 2 个字短，改用前缀搜索 山*，匹配所有以「山」开头的片段
go会多中google、good 里也有连续的 go

03索引建在哪个字段上

每篇文章有标题、摘要和正文。我们只索引标题和摘要，把它们放进一个新字段 search_text：

ALTER TABLE entries ADD COLUMN search_text TEXT
  GENERATED ALWAYS AS (CONCAT(title, '\n', COALESCE(summary, ''))) STORED;
ALTER TABLE entries ADD FULLTEXT INDEX ft_entries_search (search_text) WITH PARSER ngram;
设计为什么
生成列（GENERATED … STORED）值由 MySQL 根据标题和摘要自动算出来，Go 代码不用管。标题一改它就跟着变，永远不会不一致；加这一列时，已有的 4 万行也自动算好了
不索引正文正文可能有几十 KB，按 2 个字一切，索引会膨胀好几倍。看标题和摘要，基本就能知道文章讲什么
摘要先转成纯文本，最多 500 字原来摘要里存的是 <p>、<a href=…> 这样的原始 HTML，会把 href、div 也存进索引。入库时由 fetcher.PlainText 去掉标签、解码 &ldquo; 这类实体

04一次搜索的完整流程

以在侧栏输入「鲸鱼 海豚」为例：

  1. 前端发出请求 GET /api/search?q=鲸鱼 海豚。
  2. handler（search/handler.go）取出 q 和当前登录的用户 id，交给 service。
  3. service（search/service.go）把用户输入改写成 MySQL 的搜索语法：鲸鱼 海豚 → +"鲸鱼" +"海豚"。下一节详细讲。
  4. repo（search/repo.go）执行 SQL：查索引、过滤权限、排序，最多取 30 条。
  5. 前端在右侧面板列出结果。点标题在新标签页打开原文，没订阅的博客旁边有「订阅这个博客」按钮。

第 4 步的 SQL，去掉细节后是这样：

SELECT 文章和博客的信息
FROM entries e
JOIN feeds f ON f.id = e.feed_id
LEFT JOIN user_entries ue ON ue.entry_id = e.id AND ue.user_id = 我
WHERE MATCH(e.search_text) AGAINST ('+"鲸鱼" +"海豚"' IN BOOLEAN MODE)   -- 查倒排索引
  AND (   (f.in_pool AND f.disabled_at IS NULL)    -- 没失效的博客池文章
       OR ue.user_id IS NOT NULL )                 -- 或者是我自己的文章
ORDER BY 相关度 DESC, 发布时间 DESC
LIMIT 30
权限条件很重要。博客池是公开的，谁都能搜。但如果 bob 私人订阅了一个不在博客池里的博客，alice 不应该搜到它，否则就能看出 bob 订阅了什么。测试里专门验证了这一点：把这个条件删掉，测试就会失败。

05用户输入怎么处理

MySQL 的 boolean 模式有自己的一套小语法：

符号在 MySQL 搜索里的意思
+词必须出现
-词不能出现
"一个短语"按短语连续匹配
词*前缀匹配
( ) ~ < > @分组、降低权重、调整权重等

我们的做法：先把用户输入里的这些符号都换成空格，再由程序自己拼出 +"词"。这样用户输入的内容只会被当成「要找的词」，不会被当成命令。

这样做真的好吗？用户想用正则表达式怎么办？

  • 这些符号本来就不是正则表达式，是 MySQL 自己的搜索语法。保留它们也换不来正则功能。
  • 全文索引根本不支持正则。正则要用 WHERE search_text REGEXP '…'，它和 LIKE 一样用不上索引，每次都要全表扫描；写得不好的正则还会非常耗 CPU（MySQL 用 regexp_time_limit 限制它的执行时间）。把这个能力开放给所有用户，等于给了每个人一个拖慢数据库的按钮。
  • 不去掉会怎样？比如用户输入 分布式"（多了一个引号），程序拼出来的 +"分布式"" 引号就不成对了，查询可能报错或者变成意想不到的意思。
  • 代价：真想排除某个词（-广告）的用户，现在做不到；C++ 会变成 C，搜出很多无关的结果。
结论：对「读博客的人」来说，现在的做法是合适的默认值。如果以后确实有人需要，可以有选择地支持一两个语法，比如 -词 排除。做法是程序自己识别 - 开头的词再拼成 -"词"，而不是把原始输入直接交给 MySQL。正则则不建议支持。

另外两点：查询字符串是作为参数（SQL 里的 ? 占位符）传给数据库的，不拼接进 SQL，所以没有 SQL 注入的问题；最多只取前 8 个词，防止有人输入几百个词拖慢查询。

06相关度是怎么算的

MySQL 文档说明，InnoDB 全文索引用的是 TF-IDF 的一个变体：

一个词的分数 = TF × IDF × IDF
TF  = 这个词在这篇文章里出现的次数
IDF = log10( 文章总数 ÷ 包含这个词的文章数 )
多个词：把每个词的分数加起来
  • TF（词频）：在一篇文章里出现得越多，这篇文章越可能是在讲这件事。
  • IDF（逆文档频率）：越少见的词，越有区分度。「的」几乎每篇都有，命中它说明不了什么；「鲸鱼歌声」只有两篇有，命中它就很有说服力。

用真实数据算一遍：搜「周末」

文章「周末」出现次数（TF）MySQL 给的分数分数 ÷ TF
因为闲得受不了而写了一个 App416.304.07
人到三十416.304.07
写给沐沐的信: 让我们一起来搞定312.224.07

最后一列都是 4.07，说明同一次搜索里，分数和出现次数严格成正比。这个 4.07 就是 IDF × IDF：同一个词对所有文章来说都一样，所以它不影响谁排在前面。

照公式自己算：一共 37721 篇文章，283 篇含「周末」，IDF × IDF = log10(37721 ÷ 283)² ≈ 4.51，和实际的 4.07 有出入。InnoDB 用的「文章总数」是它在索引内部维护的统计数，不是 COUNT(*)。我试过重建索引（猜测是删除的行还留在索引里），数值反而变了，所以没能精确复现。不过因为它不影响排序，没有继续深究。

这个公式解释了上次发现的排序问题：分数只看出现了几次，不区分出现在标题还是摘要。所以摘要里写了 4 次「周末」的文章，会排在标题就叫「周末的 3 种过法」的文章前面。

07局限，以及在 MySQL 里还能怎么改进

局限可以怎么改进
标题没有加权把标题在 search_text 里重复一次（简单粗暴但有效），或者排序时对标题命中额外加分
英文会匹配单词的一部分（go 中 google）对纯英文的词，再用 REGEXP '\\bgo\\b' 过滤一遍命中的结果（只在已经命中的几十行上跑，不是全表）
没有同义词、拼写纠错MySQL 做不到，需要换专门的搜索引擎（见下一节）
搜「如何入门编程」找不到「新手指南」这是「按意思找」，属于向量检索，第一版不做

08还有哪些更好的搜索方案

方案好在哪代价适合我们吗
MySQL FULLTEXT + ngram（现在）零额外组件，数据不用同步，写进去马上能搜排序简单，没有纠错和同义词，英文会多中第一版
Meilisearch单个程序就能跑，内置中文分词，支持拼写纠错，结果排序好，开箱即用多一个服务；要把 MySQL 的数据同步过去升级首选：单台 VPS 也跑得动
Elasticsearch / OpenSearch + IK 中文分词功能最全：同义词、高亮、聚合、复杂排序，业界标准跑在 JVM 上，要几 GB 内存，运维复杂；同样要同步数据上云以后：AWS 上有托管的 OpenSearch
Bleve（Go 写的搜索库）直接嵌进 Go 程序，不用另起服务索引存在一个进程的本地文件里；我们的 API 和 Worker 是两个进程，都要读写同一份索引，很麻烦不适合
PostgreSQL + zhparser / pg_jieba真正的中文分词，排序可调要换数据库不适合：技术栈已定为 MySQL
向量检索（语义搜索）按意思找：「新手怎么学编程」能找到「零基础入门指南」每篇文章都要用模型算一个向量（花钱、花时间）；精确词匹配反而不如关键词搜索以后：适合给 chatbot 推荐用

现在业界常见的「最好」做法是混合搜索（hybrid search）：关键词搜索负责「精确命中」，向量检索负责「意思相近」，两边的结果再合并、重新排序。对这个项目来说，路线是：

  1. 先在 MySQL 里给标题加权，成本最低。
  2. 如果文章多到查询明显变慢，或者确实需要纠错、同义词，换 Meilisearch。
  3. 做 chatbot 推荐时，再考虑加向量检索，和关键词搜索组合成混合搜索。

09面试怎么讲

被问「做技术选型时怎么取舍」时，可以讲「为什么用 MySQL 全文索引而不是 Elasticsearch」这个故事，完整版在 docs/dev-problems.md。主线是：

  1. 需求：从约 4 万篇中文文章里按关键词找文章，中文没有空格，LIKE 又用不上索引。
  2. 比较方案：Elasticsearch 功能最强但要几 GB 内存，VPS 只有 1～2 GB；MySQL 的 ngram 不需要词典，数据也不用同步。
  3. 决定和验证：选 MySQL，用 11 个真实关键词验证，查询都在 50ms 以内，并用测试保证搜不到别人的私人订阅。
  4. 说清局限，定好什么时候换：标题没加权、英文会多中；先在 MySQL 里改进，真不够用了再换 Meilisearch。
面试官看重的不是「用了最强的技术」，而是知道每个方案的代价，选了适合现在规模的那个，并且清楚什么时候该换。
