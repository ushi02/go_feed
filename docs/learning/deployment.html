04每一步做了什么、为什么这样做

第 0 步：准备

生产环境只部署 main 分支。代码已经通过 PR #1、#2 合进了 main。服务器 clone 下来的最新 commit 是 bea768e，也就是第 2 个 PR 的合并。

第 1 步：创建 EC2 实例

选项选了什么为什么
区域悉尼 ap-southeast-2原计划用东京，但新账号的控制台不能切换区域。RSS 阅读器对延迟不敏感
机型t4g.small（2 核，2GB 内存）Free plan 能选的 2GB 机型里最便宜。t4g 用的是 ARM 芯片（AWS Graviton）
ARM 要改代码吗不用镜像在服务器上构建，构建出来就是 ARM 版本。Go 用 CGO_ENABLED=0 编译，不依赖 C 库。mysql、caddy 的官方镜像都有 arm64 版本
系统Ubuntu 24.04资料最多，出了问题容易查到
密钥~/.ssh/go-feed.pem，权限 chmod 600SSH 用这个私钥证明是你本人。文件权限太宽的话，ssh 会拒绝使用它
安全组22 只允许你的 IP；80、443 允许所有人网站要让所有人都能访问。SSH 是登录服务器的入口，网上一直有程序在扫描 22 端口

创建时看到警告 Rules with source of 0.0.0.0/0 allow all IP addresses…：对 80/443 来说，这正是我们要的。Let's Encrypt 签发证书时，也要从外部连进来验证。

第 2 步：Elastic IP

EC2 默认分配的公网 IP，在机器停止再启动后会变，DNS 记录写的是 IP，IP 一变网站就打不开了。Elastic IP 是固定的 IP，这次分配到的是 13.236.88.164。

Elastic IP 没有绑定在运行中的机器上时也会收费。以后删除这台机器时，要记得 Release 这个 IP。

第 3 步：DNS

ushi02.live 是在 name.com 买的，但域名服务器交给了 Cloudflare，所以 DNS 记录要加在 Cloudflare 里。加了一条 A 记录 gugu → 13.236.88.164，选灰色云朵（DNS only）。如果选橙色，浏览器连到的是 Cloudflare 的服务器，而不是你的机器：Caddy 申请证书可能失败，咕咕的流式回答也可能被 Cloudflare 攒起来，最后一次性发出。

第 4 步：Docker 和 swap

swap 是硬盘上划出的一块空间。内存不够用时，系统会把暂时用不到的数据搬到这里，给正在运行的程序腾出内存。

机器的内存一共只有 1.8Gi（标称 2GB，减去系统保留的部分）。--build 构建镜像时，npm 打包前端和 Go 编译会同时占用几百 MB 到 1GB。如果没有 swap，内存一满，Linux 会直接杀掉占内存最多的进程（OOM killer），构建失败，日志里可能只有一个 Killed。加 swap 以后，构建会慢一些，但能完成。

sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile   # 创建 2GB 文件，只有 root 能读（内存里的数据可能包含密码）
sudo mkswap /swapfile && sudo swapon /swapfile               # 格式化成 swap，并立即启用
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab    # 重启后自动启用；只运行一次

先检查后操作：这次登录后先用 free -h 看了一下，确认 swap 是 0B 才加的。swap 命令重复运行会出问题：fallocate 报错，/etc/fstab 里会多出重复的一行。

第 5 步：Deploy key 和 clone

仓库是私有的，服务器需要一把钥匙才能 clone。这里没用你自己的 GitHub 账号，而是用了 Deploy key：

你的个人 SSH keyDeploy key（这次用的）
能访问什么你账号下的所有仓库只有 ushi02/go_feed 这一个
能不能写能不能（没勾 Allow write access）
服务器被攻破时攻击者能改你所有的仓库攻击者只能读这一个仓库

ssh -T git@github.com 返回的是 Hi ushi02/go_feed!（仓库名），而不是 Hi ushi02!（用户名），说明 GitHub 认出了这是 Deploy key。第一次连接时提示的指纹 SHA256:+DiY3wvv… 和 GitHub 官方公布的一致，所以可以放心输入 yes。

第 6 步：.env

变量作用
DOMAINCaddy 为这个域名申请证书
MYSQL_ROOT_PASSWORDMySQL 管理员的密码，备份时用
MYSQL_USER / MYSQL_PASSWORDapi 和 worker 平时连数据库用的账号。和 root 分开，程序就不需要管理员权限
DEEPSEEK_API_KEY咕咕调用大模型用的密钥

密码用 openssl rand -hex 16 生成，结果只含字母和数字。原因是密码会被拼进 MYSQL_DSN：go_feed:密码@tcp(mysql:3306)/…，如果密码里有 @ 或 /，这个连接字符串就会被解析错。

为什么 DeepSeek key 要填两次：.env 在 .gitignore 里，不会进仓库，git clone 也就不会把它带到服务器上。Mac 上的 .env 是本地开发用的，服务器上的是生产环境用的，两个文件互相独立。密钥不进仓库是 CLAUDE.md 里规定的。

写密钥时用 nano 编辑文件，不要用 echo "KEY=..." >> .env，否则密钥会留在 shell 的命令历史里。

feed response exceeds 2 MiBfetcher 规定最多读 2 MiB，这个博客的 RSS 更大，被拒绝了。这是防护措施，防止一个超大响应把内存占满防护生效
round done: 1 feeds …每一轮，worker 会一直领取到期的博客，直到没有为止。第一轮应该一次处理了上千个；现在的每一轮只有零星到期的，所以只有 1 个正常

抓取失败的博客不会一直重试：失败越多，下次重试隔得越久（1、2、4…小时，最多 32 小时）。这在 worker.go 里叫 backoff（退避）。连续失败太多次，或者对方返回 410（Gone，表示永久删除），这个博客就会被停用，不再抓取。

想看第一轮的规模，可以在服务器上运行：docker compose -f docker-compose.prod.yml logs worker | grep "round done" | head -3

备份只有 2.1K

文件的时间是 00:36，和 worker 启动是同一分钟。backup 容器在 api 健康后马上做了第一次备份，那时表刚建好，博客池可能还没导入完，所以几乎是空的。下一次备份在 24 小时之后，那时就会有博客池和文章，文件会大很多。手册里说「MB 级别」，指的是有数据之后的大小。

06一次错误的诊断

先区分「被拒绝」和「超时」

Connection refused 很快就失败

请求到达了服务器，服务器回复：这个端口上没有程序在监听。

例子：10-30 启动前，80 和 443 在 0.2 秒内就被拒绝了。这时安全组已经放行，只是 Caddy 还没启动。

Timeout 一直卡住

请求在途中被丢掉了，没有任何回应。AWS 安全组拦下请求时就是这样，网络或代理屏蔽某个端口时也一样。

当时的判断错在哪里

Claude 从自己的沙箱测试，80/443 被拒绝，22 超时，就断定是「安全组记的是旧 IP」。实际情况：

检查结果
安全组 SSH 规则里的 IP就是 153.179.155.201，和你当时的 IP 一样
你从自己的终端 SSH成功
沙箱连 github.com:22同样超时，说明沙箱连任何 22 端口都会超时
错误在于：用一个本身有限制的环境去测试，再把测试结果当成服务器的问题。正确的做法是先测一个已知正常的目标作为对照组，比如 github.com:22。对照组也失败，就说明问题出在测试环境。后来测 3306 时就先做了对照，对照组也超时，所以那一项交给你在本机测。

10-29 那次卡住的真正原因没能确定。规则没改过，第二天就能直接登录了，比较可能是你本机网络或 VPN/代理的临时状态。下次再遇到，在你自己的终端里运行：

curl -s https://checkip.amazonaws.com     # 现在的公网 IP，和安全组规则里的 IP 比一下
nc -vz -G 5 13.236.88.164 22               # 22 是超时还是被拒绝
nc -vz -G 5 13.236.88.164 443              # 对照：443 能不能连上
nc -vz -G 5 github.com 22                  # 对照：你的网络能不能连上任何 22 端口

08面试可能会问

为什么用一台 VPS + Docker Compose，不用 ECS 或 Kubernetes？
用户很少，一台 2GB 的机器就够用。Compose 用一个文件描述 5 个服务和它们的启动顺序，本地和线上用的是同一套配置。迁移到 AWS 托管服务的方案，我单独写在了设计文档里。
HTTPS 证书是怎么来的？
Caddy 读到 Caddyfile 里的域名后，会自动向 Let's Encrypt 申请证书，到期前自动续期。证书存在 caddy_data volume 里，重建容器也不会丢。前提是 DNS 已经指向这台机器，所以 DNS 要先配好，确认生效后再启动 Caddy。
MySQL 怎么防止被外部访问？
两层：安全组不开 3306；compose 里 MySQL 没有 ports:，只在 Docker 的内部网络里能访问。上线时用 nc 从外部测试 3306，并用 443 做对照。
服务之间的启动顺序怎么保证？
用 depends_on 加 condition: service_healthy。MySQL 健康以后才启动 api；api 执行完迁移、健康检查通过后，worker、backup、caddy 才启动。MySQL 的健康检查特意用 TCP（-h 127.0.0.1），因为第一次初始化时，MySQL 会先启动一个只监听 socket 的临时服务器，用 socket 检查会误判为已就绪。
部署时遇到过什么问题？
SSH 连不上时，我先区分是「超时」还是「被拒绝」，来判断请求有没有到达服务器。有一次结论下早了：测试环境本身连不了任何 22 端口，我却以为是安全组的问题。后来测了 github.com:22 做对照才发现。从那以后，我会先确认测试环境本身没问题，再相信测试结果。
部署在 2GB 内存的机器上，有什么要注意的？
镜像是在服务器上构建的，构建时内存会冲高，所以加了 2GB swap，防止 OOM。运行时 5 个容器加起来大约占 1GB，还剩 800MB 左右可用。
